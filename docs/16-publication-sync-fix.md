# 审核通过后客户端不更新：修复与部署

此补丁继续使用 `feat/admin-console` 分支和 PR #4。应用/API版本仍为0.4.0，以Git提交SHA及前端构建文件识别补丁；不修改API协议、数据库迁移、地图revision或素材。

## 本次确认的事实

2026-09-23只读核对 `https://2512921.cn`：服务返回v0.4.0、后台启用；首页脚本为修复前的 `index-CQXYMQJx.js`。公共校园图revision=3，83个公开点位当时全部为正式revision=1，定位和点击范围与初次导入数据一致。公共JSON响应具有 `Cache-Control: no-store`。

这不能证明用户的那次审核成功落在此站点的公开数据中。需要用具体点位名称/ID和后台完整地址继续对照正式版本、审核记录、可见范围及实际部署。不能单凭“客户端未变”断言是缓存，也不能仅凭后端已有审核代码断言线上发布一定成功。

源码确认了两处独立的问题：

1. 原客户端只在打开页面/出错重试时读取数据，已打开的页面不会主动感知审批发布。
2. 原后台“点击定位”、拖动紫色锚点、输入X/Y只改`anchor`；客户端选中范围与定位使用`polygon`。因此只移动锚点并不会移动可点击区域；已有建筑名称印在图片中，也不会因更改锚点而挪动。

## 改动后的行为

### 客户端同步

- 页面可见时每30秒检查已发布目录；返回页面、重新聚焦窗口、网络恢复时立即重新读取。
- 同源浏览器中，后台发布成功通过BroadcastChannel发送无数据的更新通知，公开页面收到后重读公共API。其他浏览器/设备通过定时读取或重新打开取得更新。
- 不支持BroadcastChannel时，聚焦与轮询仍有效。后台标签页不轮询，返回时补读；网络延迟/后台浏览器调度会影响实际更新时间，不承诺固定30秒内完成。
- 新增“刷新地图”按钮。公共JSON读取使用`cache: no-store`；图片仍使用原来的版本化地址。
- 刷新失败时保留上次成功读取的地图并明确提示，不显示同步成功。请求有30秒超时；卸载时取消。旧请求期间发生发布，丢弃该次旧结果并补发一次请求。
- 无变化时保留地图、图层和点位对象引用。更新其他地点不会重建地图或改变当前缩放；选中地点的点击范围改变时才重新定位。下架的选中点会关闭详情并清除分享地址中的点位/楼层参数。
- 搜索词、类别与当前点位在刷新时保留。此机制只读公开接口，不接收后台草稿数据或权限。

### 后台位置调整

- “移动整个点位”、拖动紫色圆点、编辑定位X/Y：对锚点和整个点击多边形应用同一位移，保留原有形状及原图像素坐标。
- 如果整体移动会越出图边界，拒绝该次移动并提示原因，不能把各顶点分别截断而扭曲范围。
- “只移新增文字”：仅在已启用新增文字时显示，专门调整文字锚点；不移动点击范围。
- 矩形、多边形、顶点拖动仍用于调整点击范围。所有修改仍须保存草稿、提交、由独立账号审核；无前端绕过审核。
- 底图里烧录的名称保持原像素，不会随数据库点位变更。新增SVG文字与烧录名称应明确区分。
- 补丁不会自动改写历史点位坐标。此前只改锚点的记录需检查实际点击范围，按正确区域调整并重新走审核；不要盲目重复位移或重新导入旧资源包。

### 发布结果核验

- 审核成功后先显示保存的正式版本号，再从公众使用的点位详情和地图features接口回读。
- 对照正式revision、名称/别名/分类/介绍、图版本、锚点、多边形和新增文字开关。全部匹配才显示“公开接口已核对”，并给出打开公开地图的入口。
- 下架或内部/受限内容，核对点位详情和点击范围均不对公众返回。
- 网络超时、版本不同、几何不一致分别提示待核查；核验失败不会撤销已提交的审核，也不会再次执行发布。可用“核对公开端”按钮重新读取。
- 回读只验证该时刻的同源公开API，不证明另一域名、另一个设备或旧版页面已刷新，也不证明底图内文字被改动。

## DeepSeek部署步骤

先确认工作目录确为当前TwinNKU仓库，保留现有`.env`、数据库与资源卷。检查`git status`，存在本地修改时先处理，不执行强制重置。

```bash
git fetch origin
git switch feat/admin-console
git pull --ff-only origin feat/admin-console
git rev-parse HEAD
docker compose build web
docker compose up -d --no-deps web
docker compose ps web
```

本次只需要重新构建并替换web容器，不能仅执行restart。API、PostgreSQL与原图片包不需要重新导入；不重复创建管理员，不删除卷，不运行旧资源包覆盖正式点位。

如果实际站点并非由仓库Compose的web容器提供静态页面，应更新实际Nginx静态目录中的这次`apps/web/dist`构建，并核对域名真正返回的HTML及JS资源。不要仅根据容器“运行中”认定页面已更新。

上线后浏览器刷新一次以加载新版JS。已有旧版页面无法自动获得它尚未包含的新同步逻辑。新版应出现“刷新地图”“移动整个点位”“核对公开端”。后台版本字符串仍为0.4.0不代表部署失败，需核对实际提交SHA和构建资源。

## 验收

1. 用编辑账号对一个已确认的点位小幅调整点击范围，保存草稿。此时公开端保持旧版本。
2. 另一个符合权限的账号审核，记录正式vN和公开核验结果。公开可见点必须核验成功；内部点应显示公众端不展示。
3. 保持一个新版客户端窗口已打开：同浏览器发布后、切回页面后或下一次可见轮询后，确认新区域可点击，旧区域不再命中该点（重叠建筑另行核对）。查看搜索结果与详情的新资料。
4. 在其他地点保持缩放，发布不相关点位，确认视角未被重置。断网后手动刷新，旧地图保留且提示更新失败；联网后可恢复。
5. 单独测试“只移新增文字”，确认点击范围保持原位；再测试整体移动，确认文字与点击范围一起移动。图片原有印刷名称不变。
6. 测试下架、内部可见和未审核草稿，确认公众目录/点击范围/详情的状态正确。需验证手机与桌面真实交互，此补丁的单元测试不替代此步骤。

若仍不一致，请提供：后台完整URL、具体点位名称/ID、后台“正式vN”、审核后的核验提示、公众页面URL、当前部署提交SHA。不要提供密码、Cookie或CSRF token。

| 核对现象 | 下一步 |
| --- | --- |
| 后台正式版本仍是v1，只有草稿/待审核版本变了 | 核对是否真正完成独立审核发布，以及操作记录 |
| 后台正式vN、同域公共API仍v1或无此点位 | 核对可见范围、实际服务、数据库连接、反向代理/缓存与是否被旧资源覆盖 |
| 后台和公共API一致，旧页面未更新 | 核对是否已部署并加载本补丁；新版点“刷新地图” |
| 点击范围更新，但原图内名称没有挪动 | 属于图片烧录文字，需要另行审核底图修改，不是发布失败 |
