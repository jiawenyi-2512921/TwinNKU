## 1. 实施原则

基础前后端先在服务器运行，后续每个模块独立开发、测试、部署和启用。不要等全校素材齐全再联调；不要把未经验证的接口写进完成清单。

每个模块必须提交：代码、迁移（若有）、契约更新、前端集成、关键测试、资料来源、启用条件与回退办法。代码合并不代表自动开放功能。

## 3. 第一次贯通优先级

地图修订与基础部署可以分别推进，但第一个垂直场景必须尽早完成：一个点位 → 一份审核讲解 → 一条真实平台调用 → 一个focus_point动作 → 一个VR入口 → 一次追问保持上下文。

这个场景验收后再扩大点位数量；不先铺满几十栋楼再确认智能体是否能调用。平台API契约验证属于M04前置探索，可在M00后立即进行，不需要等M03全部结束。

## 4. 前端文件边界

- `features/campus`：校园元信息与目录；M00已有。
- `features/map`：Leaflet生命周期、坐标适配、图层；不负责问答。
- `features/points`：点位详情、别名、来源和相关资源。
- `features/routes`：起终点表单、请求与路径segment，不实现另一套算路算法。
- `features/vr`：官方资源打开方式和用户手势，不访问跨站DOM。
- `features/floors`：楼层切换与房间选中，复用坐标适配。
- `features/chat`：会话、输入、事件序列、ActionDispatcher、取消。
- `features/tours`：步骤、已参观点位、调整请求和回顾。
- `features/admin`：经鉴权的编辑、审核和统计页面；不能把后台权限写成前端常量。

各模块通过typed API、统一资源ID和应用上下文组合。组件不得直接读写其他模块私有状态。网络调用支持AbortSignal；effect卸载后不得改状态。

## 5. 后端模块接入模板

每增加一个模块，在 `app/modules/<module>/` 建立 router.py、schemas.py或复用contracts、service.py、repository.py及测试。`main.py`只组合router和基础中间件。

顺序：

1. 在完整机器契约中核对请求响应和错误，不自行发明相同含义的新字段。
2. 迁移新增表/索引；禁止应用启动时create_all修改生产结构。
3. service实现权限、版本和状态机；repository用参数化查询。
4. API实现与计划契约保持同operation_id，将该计划端点移出planned_contract。
5. 导出OpenAPI和前端类型；新增跨模块验收。
6. 灰度部署，数据准备完成后开启该能力；异常可关闭能力保留基础站。

## 6. 开发顺序与工作包

不按旧日期制定未经确认的每日排期。使用可验证里程碑：

- A：M00部署且外部HTTPS可访问，备份/日志路径明确。
- B：一个点位贯通智能体、地图与全景；确认平台协议。
- C：扩充点位、室外路网和3条主题；建立资料更新流程。
- D：楼层样板与研学调整；运营后台完善。
- E：真实试用、修复、演示录制及材料。

建议小团队按前端、后端/平台、资料/路网、验收/演示分工。可由同一人承担多个角色，但审核责任和验收结果必须明确；不把人员安排或截止日期当作已获用户确认。

## 7. 合并门槛

接口兼容、关键测试通过、无秘钥和未公开素材、OpenAPI无漂移、对应文档更新。涉及权限/路网/内容发布须有人工核查证据；低影响样式修改只需构建和视觉检查，不编写照抄实现的测试。
