# 面向比赛与持续运营的下一阶段计划

2026-09-24早期产品决策稿；最新完整要求见[21](21-project-master-spec.md)和[29](29-sprint-backlog.md)。本文是建议与验收目标，不是已上线能力清单。最新地图修正由后台正式记录决定；本文不改变底图、点位坐标或用户确定的图内文字风格。

## 1. 对当前作品的判断

现有产品已经有可用基础：高清校园地图、83个命名点位、20栋楼层资源目录、标注图查看、员工角色与审核、外部VR入口维护。交付清单为96层100图；具体线上资源状态仍需部署验收。新增83点介绍包尚须导入审核。

目前的主要缺口是主动导览能力：没有真实智能体联动、主题参观进度与学习反馈，也没有实际用户数据证明效果。单纯继续增加页面和按钮，难以形成鲜明作品。目标应确定为：

> 面向公众与研学团体的南开校园文化智能导览，让用户通过一句话找到内容、进入相关场景，并完成一次有收获的线上参观；宣传部门能持续审核和更新。

“顶尖”应转为可检验的质量要求：有依据的讲解、自然连续的操作、优秀的手机体验、可审核的运营，以及实际试用效果。功能数量和数据库条数不能单独证明领先；不承诺比赛名次。

## 2. 前台改为什么样

现有左侧品牌介绍、搜索、筛选、长目录和右侧大面积装饰标题同时存在，挤压主地图。地点详情的楼层页签与楼层入口重复；某些楼栋没有资料却仍可按类别推断出入口。每增加模块继续常驻一块，会加重问题。

建议下一版采用**以地图为主、按任务展开的单一内容面板**。保留南开紫作为少量强调色，正文使用更深颜色；压缩装饰性占位，增加留白用于内容层级。

| 使用状态 | 桌面端 | 手机端 | 退出后保留 |
| --- | --- | --- | --- |
| 初次进入 | 大地图；左上紧凑搜索；简短的探索入口 | 地图铺满主体；顶部搜索 | 地图视角 |
| 搜索地点 | 搜索框下临时结果，显示名称和类别 | 搜索暂时展开为列表 | 选中地点后收起结果 |
| 自主看地图 | 一个展开式目录，可筛选/搜索全部点位 | 从底部打开目录 | 类别条件 |
| 选中点位 | 一个约360px侧面板：名称、短介绍、可用内容 | 底部卡片，可展开详情 | 选中状态、地图缩放 |
| 看楼层 | 楼层图成为主要查看区，工具条只含层/分区/缩放/返回 | 全屏看图，触控缩放 | 原地图位置和点位 |
| 看全景 | 选择该点场景；外部链接新窗口，保留返回上下文 | 同样明确进入/返回路径 | 参观进度 |
| 询问智能体（待实现） | 对话复用同一侧面板，地点简卡留在对话内 | 底部对话展开；不盖住所有操作 | 当前点位、楼层、参观步骤 |
| 主题导览（待实现） | 简洁步骤条、当前讲解、下一站 | 同一底部卡片切换导览内容 | 已参观记录 |

具体取舍：

- 去掉常驻大段欢迎文案和空白图标横幅；品牌只保留紧凑标识。
- 左侧完整目录按需打开；选点后不同时摆两列长列表。
- 每个详情最多突出一个当前主操作；楼层、VR入口只在有已发布资料时出现。网络读取失败显示重试，不误报“无资料”。
- “看地图”始终能用；“问导游”“主题参观”随真实模块完成逐步开放，不摆不能使用的功能按钮。
- 名称继续写在原图中，不恢复满屏编号或常驻白底标签。搜索、选中轮廓与详情标题负责低缩放下的识别。
- 手机触控按钮至少44px；详情与输入框兼容系统键盘；来源折叠；长名称换行；保留复制链接和键盘焦点。
- 前后台分开设计：访客体验注重阅读和引导，后台注重表单、对照和审核效率。

建议先交付地图、详情、楼层三种状态的真实数据版本，再接入对话。验收使用“从首页找一栋楼 → 看介绍 → 打开楼层 → 返回地图”和“复制链接给他人”两条完整任务；比较用时、误点和返回成功率，而不仅看一张截图。

本文件起草时仅完成介绍排版。后续同日增量已实现地图主界面、折叠目录、单详情与楼层大图入口；交付边界/待执行真机验证见[30](30-interface-release.md)。AI与主题仍未实现，完整冲刺规范现以[21](21-project-master-spec.md)起为准。

## 3. VR点位多于建筑，应该如何处理

建筑是校园空间的一种类型，VR场景是资源，不要求一栋建筑只对应一个场景。目前已有“同一点位多条VR链接”的能力，可以直接维护图书馆外观、门厅等不同视角。不要为每张全景复制一个建筑或在地图上新增编号。

| 官方VR资源类型 | 当前可执行做法 | 后续数据能力 |
| --- | --- | --- |
| 已有建筑的不同视角 | 在同一点位下增加多个已审核VR资源，标题说明视角 | 增加楼层、主题和排序字段 |
| 湖泊、广场、雕像 | 对应已有景观点位；若确有新地标，由人工定位并审核新增 | 统一地点类型与关联关系 |
| 一个场景覆盖多个地点 | 先由内容负责人确定主关联，描述可见内容 | 共用scene_id，多点关联，避免复制URL和维护冲突 |
| 另一校区的场景 | 留在待整理清单，不投到津南地图坐标 | 有对应底图与审核资料后再开启新校区 |
| 无法定位或链接无法直达具体场景 | 暂不发布为地图点位；核实标题、校区与可分享URL | 可进入独立场景目录，地图定位允许缺省 |

第一批选20—30个有内容价值、能稳定直达的场景，优先覆盖核心讲解点。数量是建设目标，不是已接入数量。资源台账至少包括官方标题、来源页、分享URL、校区、关联点位/楼层、最后核对时间、可见内容摘要、审核状态。不能假定官网下载页面地址等于稳定场景地址，也不能假定第三方允许iframe或远程控制。

## 4. 最值得投入的三个差异点

### 4.1 会操作界面的校园导游

用户问“这里是什么学院？”能带入当前地点；问“带我看看图书馆”能聚焦图书馆并给出已审核全景；接着问“二层有什么？”能保持建筑上下文并展示已有二层图。答案含依据，动作引用系统已有ID。

实现路径：真实NK-GeniOS API核验 → 后端适配 → 从已发布资料检索 → 服务端验证动作与公开状态 → 前端执行白名单动作。先支持focus_point、show_floor、open_vr；主题进度完成后增加show_tour。沿用docs/05的协议命名，不另创一套。

不能根据平台名字猜API；需要正式请求/响应样例、可用认证方式、流式/会话行为与服务端连通性。密钥只留后端环境。用户移动到新地点时旧回答不能突然把地图拉回；取消、超时、空检索、无权资源都要可解释。涉及校门开放、参观预约等政策，只有明确有效的正式资料才作答，缺资料给官方渠道。

### 4.2 有学习目标的线上主题参观

优先完成一条“南开校史与爱国传统”旗舰体验，核心可选周恩来雕像和三座复建建筑，并加入经过核实的校史内容。参观顺序先是线上内容编排，不在未经核实的路网上画步行线路或报告距离。

每站用“一个核心故事＋一个可观察的画面＋一个思考问题”组织；用户可选简洁/深入讲解，随时跳过，最后生成可核对的参观回顾。回顾使用已访问记录和审核内容，不让模型编造用户完成过的活动。

完成后再扩展“学科探索”“校园生活”两条主题。若要线下时长推荐，先核实入口、路网、通行和步行标定；否则明确为线上约15/30分钟的内容量选项，不冒充实测出行时间。

### 4.3 内容能越用越完善

记录匿名化的未解决问题及用户反馈，内容人员看到缺口后补充 → 独立审核 → 公开页面和知识索引更新 → 同一问题再次测试。资料revision、来源日期与最后索引版本可追踪。

这条可演示的更新过程，能回应宣传部门咨询负担、材料分散和口径管理三项实际需求。后台统计应服务处理问题，不先堆无数据支撑的大屏。

## 5. 能做到什么程度

近期仓库迭代已经完成地图、楼层与审核基础，但目前没有可据以承诺固定开发产出的工时记录。代码实现速度不能等同于官方材料审核、跨平台联调和真实试用速度。以下为依赖满足时的执行目标，需要按阶段验收调整。

| 层级 | 建设目标 | 完成标准 |
| --- | --- | --- |
| 必须做好 | 83点基础介绍、现有20栋楼层、精简访客界面 | 资料逐项审核；用户修正保留；手机完整任务顺畅 |
| 形成特色 | 8—12个核心点深度讲解、真实AI地图/楼层/VR联动、1条精品主题 | 无硬编码假回答；来源可点；场景切换正确；失败可恢复 |
| 冲刺提高 | 扩到3条主题、20—30个VR场景、参观回顾与未解决问题管理 | 内容与流程有真实试用数据，不用演示样本代替用户成效 |
| 后续运营 | 语音讲解、教师研学任务单、多语言、历史今昔对照 | 有真实需求、审核稿与可持续维护人员后逐项加入 |

当前阶段不把全校三维重建、精确室内定位、未经核验的跨楼导航、复杂虚拟人物直播列入比赛必交范围。这些会引入新数据和工程依赖，难以与现有资料准备速度匹配。

## 6. 倒排至比赛材料提交

用户提供的2026年6月《参赛指南》与2026-09-24检索到的[主办方通知](https://www.caet.org.cn/site/content/1279.html)、[赛事官网](https://aiedu.caet.org.cn/)均列报名材料截止2026-10-15。校内审核可能更早；具体赛道、资格和校内节点由项目负责人确认。本计划不是报名完成证明。

| 建议时间 | 工作 | 必须留下的证据 |
| --- | --- | --- |
| 9月25—28日 | 介绍包审核发布；地图/详情/楼层减负；并行确认NK-GeniOS实际API | 前后端版本、内容发布清单、手机两条任务录像、真实API样例 |
| 9月29日—10月4日 | 一组核心地点贯通AI问答、定位、楼层与VR；一条主题完整完成 | 可重复对话案例、动作成功/失败记录、来源核对 |
| 10月5—10日 | 按稳定程度扩展主题/VR；邀请真实用户试用；修复主要问题 | 匿名任务记录、问答评测、问题修复前后对比 |
| 10月11—14日 | 冻结新增功能，回归、整理材料、演示视频、部署与回退演练 | 可复现版本、操作视频、事实一致的指标与说明 |

关键分岔：9月28日前若平台API仍不可实际调用，立即将其列为首要阻塞，压缩多语言、音频等扩展。网页跳转到独立聊天页面不能作为系统内AI联动完成的证据；此时不能宣称已经达到完整智能体作品目标。

建议分工按责任划分为界面/联动、服务端/平台、资料/VR核对、试用/演示；人数不足可兼任，但内容编辑和审批仍须分人。每天围绕一条用户任务推进，只合入完成验收的增量，避免反复整站换方案。

## 7. 评测目标，不是现成成绩

- 准备100题固定问答集：基础事实、易混名称、当前政策、资料缺失、图上定位、跨点追问；由内容审核人判定答案和来源是否支持，分别报告准确率、合理拒答与错误引用。
- 招募至少20—30名真实体验者，覆盖校外首次访问者、校友/学生及研学组织者；不给只看演示的人记作完成任务用户。
- 测试找点、看楼层、看VR、完成主题四类任务，记录任务完成率、中位完成时间、返回失败与误触。以当前版本作同题基线，比较新版是否改善。
- 建议发布门槛：受测已知事实正确率≥95%、地点/楼层/VR动作正确率≥95%、关键权限与草稿泄漏测试零失败；达不到则修复或缩小开放范围。这些是拟定目标，必须在材料中同时注明样本量、测法和实际结果。
- 在真实中国大陆移动网络上测首屏地图可用时间、对话首字与完整响应的P50/P95；服务器位置和官方VR服务均可能影响耗时，先测量再决定缓存和资源优化，不以本地构建速度代替体验速度。

演示应完整展示一次“提出参观需求 → 导游讲解并操作地图/VR → 完成学习回顾 → 后台补资料后答案更新”。这是比单独展示地图、聊天框和管理表格更有说服力的作品主线。
