# 素材、点位与宣传部交付规范

2026-09-23最新交付决定：用户明确允许本项目图片上传GitHub，并指定GitHub为代码、部署指导及数据传输渠道。已整理地图与楼层图的版本化ZIP通过本仓库Releases交付，具体下载和服务器导入见[GitHub资源交接](12-github-resource-handoff.md)。

## 1. 第一批所需材料

| 材料 | 必须包含 | 谁核实 |
| --- | --- | --- |
| 修订总规划图 | 原尺寸、当前名称、建成状态、版本、允许公开范围 | 项目资料负责人/校方 |
| 代表点位清单 | 正式名、别名、类别、简介、资料来源、入口、公开范围 | 宣传部/点位负责人 |
| 讲解词 | 核心事实、面向对象、来源、审核人、审核日期 | 宣传部 |
| 参观政策 | 生效时间、失效/更新规则、官方申请渠道 | 主管部门 |
| 全景对应表 | 点位ID、官方URL、场景标识、是否可嵌入/有事件接口 | 实际访问及平台资料 |
| 楼层样板 | 原件、有字图、无字图、房间号、公开范围、入口/楼梯核实 | 建筑负责人/现场核查 |
| 咨询样本 | 脱敏问题、分类、标准回答及来源 | 宣传部 |

“应该可以提供”不等同已提供。每份材料在交付清单标记未收到/已收到待核对/审核通过/撤回，不能自动从附件上传状态推断公开许可。

## 2. 点位表

建议用UTF-8 CSV或表格交付，列：external_code、name、aliases（分号分隔）、category、summary、source_title、source_url、source_date、visibility、reviewer、reviewed_at、notes。

external_code只是导入批次中对照码，正式id由系统生成并保存映射。相同名称不是自动合并依据。类别只用contracts中的枚举；别名不替换正式名。

## 3. 标注文件

每个地图版本包含manifest.json、approved-image文件、point-geometries.json、entrances.json、route-graph.json。manifest至少记录map_id、revision、width_px、height_px、sha256、source、reviewer。

所有坐标按原图左上角像素；输出尺寸和图像hash必须匹配。不要把手机截图当作原图定位基准。标注不可修改道路、河流与建筑相对布局。

点击多边形先覆盖建筑可识别主体；锚点用于面板与定位，入口用于导航。对建筑群、同名楼宇先建立明确point_id，不能让模型猜。

## 4. VR交付

逐条核对点位与实际场景，保存最后验证时间。公开网址不能证明拥有图片下载、镜像或重新分发许可；首版默认引用。嵌入、场景切换和事件回传分别验证，不能因为iframe能显示就宣称能控制。

场景URL当作内容数据由后台维护，不散落在React组件或prompt里。无全景点位保留文字/图片入口，不链接到随机相邻场景冒充。

## 5. 楼层交付

用户最新授权允许图片通过GitHub传输。本批运行资源包每层仍只包含labeled（已标注）与clean（无标注）两张整理图，不含实拍照片；素材传输范围与运行模块支持的文件角色分别记录。后续房间表另行核实。保留真实房间号、厕所/洗浴/楼梯/电梯等有效用途名称。标签位置与实际对应房间逐一核对，不依据AI生成文本直接录入。

“当前位置”、拍摄倾斜和公告牌边框属于展示清理事项；不得据此移动真实房间、门或墙。清理图不自动生成可走路网，路网需另外核实。

## 6. 发布前清单

来源授权、脱敏、名称一致、房间号一致、开放范围、有效时间、讲解审核、像素坐标、文件hash、VR对应、更新时间负责人。缺哪项就保持草稿或仅内部核对。

## 7. 内容更新演示

保留一条真实可复现链路：未解决问题 → 资料补充 → 审核发布新revision → 知识库同步 → 回归同一问题 → 显示新来源。记录耗时与审核人，作为持续运营能力的证据。
