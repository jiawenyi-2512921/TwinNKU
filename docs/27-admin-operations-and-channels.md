# 后台、咨询运营、权限与渠道实施细则

已实现部分见15/18/19。本文扩展的是内容源、主题、VR台账、咨询和运营，并继承现有独立审核、scope和revision检查。

## 1. 后台信息架构

常用工作区按任务组织：待办→点位与地图→楼层/VR→讲解与来源→主题研学→咨询缺口→运行质量→账号与审计。先显示“待我处理”与具体记录，不先做无真实数据的大屏。未实现工作区不开空菜单。

一条记录的统一结构：基本信息/公开版本/当前草稿/资料依据/修改差异/审核记录/公开结果验证。编辑保存与发布明确区分；操作按钮文字与后果对应，禁止“保存”暗含直接公开。

## 2. 权限矩阵与数据scope

现有角色保持：viewer、editor、reviewer、admin；以下扩展权限先以permission检查规划，新增权限字段需契约与迁移。scope按校区和明确点位，字段级敏感数据需额外授权。

| 操作 | viewer | editor | reviewer | admin |
| --- | --- | --- | --- | --- |
| 范围内读资料 | 是 | 是 | 是 | 是 |
| 编辑/保存/提交 | 否 | 是 | 否 | 是，但计入贡献者 |
| 审核/发布/退回 | 否 | 否 | 是，不能自审 | 是，不能自审 |
| 账号/角色/scope | 否 | 否 | 否 | 是 |
| 公开结果验证 | 范围内读 | 范围内 | 范围内 | 范围内 |
| 咨询缺口统计（计划） | 单独授予 | 单独授予 | 单独授予 | 可管理授权 |
| 查看原始敏感问题（默认不保存） | 否 | 否 | 否 | 不因admin自动获得全部私人信息 |
| 平台密钥 | 不通过页面返回 | 不返回 | 不返回 | 页面也不回显原值 |

操作具体权限仍以当前service为准，这张表不能作为绕过现有控制的理由。分工规则：同一次变更的贡献者、提交者均不得审核，账号换角色也不能洗掉贡献记录。管理员不可编辑自己scope以绕开特定审计流程。

未来SSO映射：校方真实身份→本系统staff account→受控role/scope；登录成功不自动成为编辑。需核验OIDC/SAML/学校自有协议、回调origin、state/nonce、签名、账号停用和登出；协议不明时保留现有受控账号。

## 3. 编辑、审核、发布与回退

保存草稿：带expected_revision和expected_point_revision；冲突409后显示最新版差异，不自动用旧表单再提交。地图、图片、VR、来源和讲解分别保持版本，不让一处改文字顺带覆盖几何。

审核界面应看“这次改了什么”：字段diff、前后图片并排/切换、坐标位置预览、来源打开、影响的公开入口/主题/知识版本。审核要求填写通过/退回理由，发布事务与审计一致。

发布成功后做公共GET核验：revision、文本、几何、资源实际可访问；若发布已成功但公网读取失败，显示“已发布，公开验证待重试”，不得回滚DB后假报失败或要求重复提交同草稿。

回退不是删除新记录：选择历史审核版本→生成新草稿→复核依赖→独立审核→发布新revision。紧急下架可立即阻止公开服务，恢复仍需明确资源/来源有效性。历史文件保留到既定保留期后再受控清理，不随意删生产卷。

## 4. 来源/知识发布管理

来源中心提供：类型、校区、标题、有效期、最后核查、关联点位、审核状态、知识同步状态。原始文件/网页摘要/实际引用片段可对照，OCR结果必须人工核对，不能直接变正式事实。

三套状态分开：内容审核状态（draft/in_review/published/retired）、外部索引状态（pending/syncing/ready/failed/stale）、资源探测状态（unknown/available/failed）。一个绿色图标不能同时代表三者。

发布后outbox同步；后台显示source_revision与indexed_revision。落后时可重试但不越权修改平台资料；撤回立即阻止业务检索。正式政策到期预警建议T-7/T-1天，没审核延期就按期失效；未提供有效期的政策进入待核实，不无限期视为当前。

## 5. 咨询归集工作流

入口：回答后的“有帮助/仍需帮助”、地图/楼层/VR纠错、无来源问题、官方申请渠道查找。用户可匿名，不强制留下手机号。必要联系信息优先在学校正式申请系统填写，本系统不复制收集。

脱敏后分类：visit_policy、campus_info、content_correction、other；内部细分原因可含missing_source、outdated_policy、wrong_resource、agent_failure、unsafe_request。正常负面反馈不是攻击。

状态：new→triaged→assigned→content_draft→reviewing→retest→resolved，或duplicate/needs_external。每次状态变化记录actor/time/reason。resolved要求指向实际修复内容/版本和复测结果，不只是点“已处理”。

| 字段 | 用途 | 约束 |
| --- | --- | --- |
| question_redacted | 内容人员理解缺口 | 去个人电话/学号/地址等，长度上限 |
| point_id/category | 归属 | 点位可空，不猜地点 |
| fingerprint | 聚合同类问题 | 不用可反推个人信息的原文当公开键 |
| occurrences/time_bucket | 高频统计 | 固定时区和窗口，去重口径明示 |
| assignee/status | 工作跟进 | scope校验，未授权不能转给其他人 |
| resolution_source/revision | 修复依据 | 必须指向实际发布内容 |
| retest_result | 是否解决 | 问题、预期、实际、审核人、时间 |

现有inquiry/stats端点仍planned，Identity中的analyst角色是旧设计。开发前决定使用细分permission还是新增角色并迁移，不能上线只有前端按钮控制的统计页。

## 6. 运营指标定义

| 指标 | 分子/分母与边界 | 误用防止 |
| --- | --- | --- |
| 内容覆盖 | 已发布有介绍点数/当前公开命名点数 | 初稿条数不算已发布 |
| 核心深度覆盖 | 达到审核模板的核心点/目标核心点 | 字数长不等于高质量 |
| 有效VR覆盖 | 已核验直达场景数/已整理场景数 | 不拿建筑数作场景总分母 |
| 问题解决率 | 经复测解决问题/进入处理的有效问题 | 隐藏困难问题不能提高比例 |
| AI正确率 | 正确且依据支持的可回答题/可回答题 | 拒答单独统计，不能靠全拒答得高分 |
| 动作成功率 | 正确执行动作/应执行动作 | 外链点击不算VR内部加载完成 |
| 完成主题 | 达到预定义完成条件的计划/开始计划 | 演示账号/内部测试剔除 |
| 时延 | P50/P95，注明地区/网络/样本 | 不用本地最快一次代表用户体验 |
| 内容更新时效 | 审核发布到公开与索引ready各自耗时 | 公开页面成功不等于知识索引成功 |

运营页应允许查看失败原因和缺口清单。流量很小时优先展示绝对数与样本，不画没有统计意义的百分比趋势。

## 7. 数据保留与隐私默认值（设计，启用前由学校确认）

- 公共地图浏览无需登录；不默认请求精确定位、相机、麦克风。
- 访客会话建议24小时有效，原始聊天建议最多7天、脱敏咨询30天、匿名聚合90天、审计180天作为讨论起点；这些不是法定期限，也不是现有设置。
- 成本/排错只保留必要的匿名指纹、错误码和资源版本。导出需权限，日志脱敏，公开演示避免显示真实访客记录。
- 用户能清除当前会话与未分享记录；删除与合规审计留存的关系须写清。备份中的保留同步按既定策略处理，不承诺即时物理抹除所有备份。
- 未经确认不上传原始私人咨询到海外/第三方模型；公众公开资料和内部数据分索引/分权限。服务器在海外的事实需纳入校方实际接入评估，不能凭开发者猜测合规结论。

## 8. 渠道集成顺序

L1：官网/公众号菜单链接到HTTPS网页，带channel参数；体验、权限和数据仍在同一网站。L2：学校站点允许时嵌入页面，核对移动端viewport、cookie、CSP/iframe策略和返回入口。L3：正式API/SDK适配不同渠道，独立client_id、额度与鉴权，复用统一service。

学校NK-GeniOS可发布多个渠道不代表本项目已连接全部渠道；渠道上线逐个验收真实请求与内容一致性。首次以网页为唯一产品，无小程序任务。跨域iframe涉及第三方cookie时不能以关闭安全属性绕过；优先顶层网页或正式授权流程。

对外API只开放读公开资料/受控访客会话，不给渠道token直接后台发布权。设版本、限流、审计、client撤销；API key不放可见网页。Webhook若未来使用须签名、时间窗、重放保护和幂等，不把任意请求当学校官方事件。

## 9. 运营闭环演示脚本

1. 访客问一条资料确实不足的问题，系统承认缺口并提供正式渠道。
2. 脱敏问题进入待处理，内容负责人认领并关联来源。
3. 编辑补充资料与讲解，另一个审核人核对通过。
4. 页面公开版本更新，知识同步状态从pending到ready。
5. 用同一问题重新测试，答案引用新版本；保存差异和耗时。
6. 原问题以复测证据解决，统计中计为一次有效改进。

演示使用测试会话并注明，不混入真实用户试用成果。这个可验证过程是宣传部门持续运营能力的证据。
